# Choosing models for the redesign

## Start with one choice

At the start of a new redesign, before private intake or specialist work, ask one question in the teacher's language. “How would you like to choose the models for this redesign? I can match models to the tasks, keep the current model throughout, or let you choose at each step. Or we can start with your course and decide later.” Show all three choices and accept the teacher's own words. A short recommendation can be “Keeping the current model is simplest for this lesson.” The teacher can defer, start immediately using the current authorised session, or change the mode later. Deferral grants no new access and starts no other model. Recommend a switch only when a concrete capability or quality benefit matters. If they have already chosen, carry that choice forward. On a resumed run use its agreed plan. Return to the source choice or teaching question as soon as this is settled. Keep the initial conversation in chat when there is no approved project yet.

- **Match models by task.** Research the capabilities that will affect the requested work. Propose a small set of exact models and assign each task and specialist to a model, receiving account and reasoning level where supported. Group roles with identical requirements. Give one sentence explaining a consequential difference. Let the teacher change the proposal and approve the named plan once.
- **Keep the current model.** Offer the actual current session and its existing account for every task and specialist. The teacher's explicit choice of that exact model and scope can approve the one-route plan. Use the same model across roles if the host can honour it. If the host would force another model or cannot verify a necessary capability, run that role's method in the approved session and label this as a single-session check. Indicate any unavailable evidence or independent check. The optional second opinion remains a separate choice at the end, including whether to accept a clearly labelled limited check if every eligible family participated.
- **Choose at each step.** Agree a shortlist of named eligible models, accounts, tasks, scopes, and supported effort levels up front. At a step change present the relevant in-plan choices together and ask which to use. That selection authorises the choice inside the approved plan. Never seek a duplicate transfer or model confirmation for that same in-scope choice. A new account, destination, model or exposure outside the approved plan needs its own updated scope.

## Research what matters at the point of use

Identify the actual current model, product, account/workspace and plan through information already available in the session or supplied by the teacher. A host name or an API catalogue alone cannot establish which models an existing subscription permits. When the model identity is hidden, report “current session, model unverified”. Never request a credential, create an API key, enable a provider or buy credit. Use only the existing authorised subscription or free resources. Keep public model research free of course content and personal identifiers.

For a recommendation, perform a **current, dated check** of the provider's model documentation, supported modalities and reasoning/effort controls, plan limits and workspace restrictions. Use a relevant task-specific evaluation or small synthetic comparison where it helps discriminate quality. Explain what the comparison measured and why it matters to the teacher. A coding or general reasoning score cannot establish pedagogical quality. Use a simple route when it works. Keep user control visible and assess routing on tasks where alternatives actually differ. [Microsoft human–AI interaction guidelines](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines/) · [Anthropic agent design practices](https://www.anthropic.com/engineering/building-effective-agents) Separate (1) documented capability, (2) entitlement and available allowance in this exact account or “unknown”, (3) a configured or requested model and (4) the model that actually ran. Reuse dated findings while they still apply. Refresh when the task, available model, host, access boundary or relevant capability changes. Don't inspect unrelated accounts or repeat the research at every turn.

Recommend a specific eligible model for each distinct task group, including quality and the lowest suitable reasoning effort, context and file limits, expected usage and relevant trade-offs. The teacher can override the recommendation. For example, a supported text model can map stated outcomes to activities; checking how a slide renders additionally needs a visual input or accessible viewer. Deeper reasoning can help reconcile contradictory assessment criteria but consumes more of a limited allowance. Model selection cannot grant the tools, sources or permissions needed for those checks. [Current OpenAI model and account guidance](https://help.openai.com/en/articles/20001354-gpt-6-and-other-models-in-chatgpt) · [Anthropic model information](https://www.anthropic.com/claude/opus) · [Gemini Apps limits](https://support.google.com/gemini/answer/16275805)

## Plan the six stages and ten specialist roles

| Tasks | Check before selecting the model or effort |
| --- | --- |
| Orchestration and setup | Reliable state and multi-stage reasoning, language, context size, structured output and local tool access. |
| Research, course mapper, active-learning researcher, AI-integration researcher | Reading and comparing relevant sources, access to original evidence, citation traceability and appropriate context length. |
| Student-experience critic and learning designer | Age, language, accessibility, workload and the ability to relate a concrete activity to the teaching outcome. |
| Assessment stage and assessment-alignment designer | Rubric reasoning, consistency, constraint handling and the approved boundary around assessments. |
| Materials stage and learning-material designer | Editing the requested file type, visual/document input, rendering or interaction tools appropriate to the deliverable. |
| Source-verification/citation auditor and evidence/feasibility red team | Independently checking exact citations, contradictory claims, feasibility and uncertainty. State when these are distinct roles using the same model. |
| Artefact accessibility/visual QA and system stage | Inspect the required delivery view, keyboard route or structured settings. Record any assistive-technology or native-run evidence that the selected environment cannot provide. |

For each planned route, show the named tasks, exact model/family, app/account, access and data scope, reasoning effort if configurable, expected usage and any approved fallback. The single-model choice covers the same ten roles and six stages. On an exceptional short course include roles that will be skipped or represented by the existing session. Do not launch extra models merely to fill the plan. Where tasks will use different providers or accounts, show what fields or files each destination receives. Approve the plan once, separately from course-source eligibility, material writes and release.

## Execute and check the route

Before each stage or delegation look up the approved route and verify that model, account, recipient, data, cost and capability remain within scope. Pass its model and supported effort through a real per-call or role control only when that host actually exposes it and the teacher has authorised it. Use the provider already authorised on the host. If only a user-facing picker exists, explain how the teacher can switch at the appropriate boundary. A running parent cannot silently replace its own model. Creating a separate session or forwarding a packet changes the destination unless the plan explicitly covers it. Never change persistent workspace or user-wide defaults merely to implement a run-local choice.

If the recommended model is unavailable, continue on the already approved current model if it can do the task in the same permitted environment. Offer a manual switch if the teacher prefers the recommended route. If a missing capability affects validity, pause only the affected check, name precisely what remains unverified and continue other tasks. An unavailable external model never justifies opening a new account or sending course data elsewhere.

Every specialist receives its task, chosen route, supported effort, approved scope and fallback from the orchestrator. It reports new needs back to the orchestrator. Record separately what was **recommended**, **configured/requested**, and **actually executed**. Use the launch receipt/session metadata, a model picker the teacher confirmed for that run, or mark execution **unverified**. A configured role profile, a model's self-report, an “Auto” slot, or the parent model alone cannot verify a child model. A documented inheritance rule establishes intended routing, not independent execution evidence.

When persisting a new run, the optional `model_routing` entry belongs to that run; older schema-8 runs can omit it. Record `mode` (match_tasks, keep_current or choose_each_step), `routes` and the teacher's `approval_reference` and `approval_digest`. In an approved project run `python scripts/validate_state.py STATE --model-plan-preview PLAN --run-id RUN` on the proposed JSON containing only `mode` and `routes`. Record the returned `plan_sha256` with the teacher’s reply when the named routes are approved. Keep a deferred choice in chat until the teacher agrees on a plan. Every route has a unique `id`, assigned `tasks`, exact `model`, `account`, `app`, `family`, `effort`, `scope`, `usage`, `checked_on` (YYYY-MM-DD) and `evidence`. Use the six skill names and the ten distributed role filenames without extensions as task IDs. Use `current` as the route ID for the approved current model. Optional `executions` entries identify `task`, `route`, `status` (verified or unverified), `observed_model` and `evidence`. Record the actual returned identity on a verified execution and investigate discrepancies before relying on the result. An opt-in second opinion remains a separate final transfer with its own approval and a search for a genuinely different model family. If all eligible families participated, the teacher may explicitly choose the least-involved family for a disclosed limited review.
