# A second opinion on the completed redesign

## The teacher decides whether to start

After the teacher's final course decision and the ordinary Step 9 response where applicable, offer one optional Step 10 in their language. “Would you like a second opinion on the redesign? You can finish now, prepare a review to run yourself, or explore a different model.” Honour an explicit request to finish or skip immediately. Do not look up a model, inspect accounts, open a file, prepare a packet or call a reviewer on that route. A missing reply leaves the optional review unstarted and the course complete. Keep any separate system-improvement work separate. This review cannot reopen a closed course run.

Treat a decline as applying only to the choice the teacher declined. If they decline a future second opinion while asking to design a lesson, continue the lesson. A Step 9 decline of process improvement alone leaves Step 10 available. When the teacher explicitly ends the interaction, or declines the last optional review after the course is complete, reply with one plain-language sentence naming the accepted items and where they actually received them. For a chat handover, say “You accepted the worksheet and teaching note here in the chat.” If no items were accepted, acknowledge that choice. Mention a saved file only after a verified write at that destination. Keep permissions, internal status, retention, future runs and scheduling out of the farewell. Stop without a question, another offer or a tool call. If the teacher explicitly asks for a second opinion or another action, follow that request and its normal approval steps.

## Pick a reviewer for this course

Ask what deserves scrutiny if it is unclear. Use the [model plan](model-plan.md) and the model family that actually did the design as the comparison point. If authorship is unknown, clarify it or offer a manual review without a claim of model independence. Include contributing families if several were involved. Ask which existing subscriptions or approved institutional tools the teacher can use, in ordinary language. An app can host several model families. A different app, agent persona or reasoning setting can still use the original family.

If the teacher wishes to explore current models, use only public, course-free queries. Check dated first-party model capabilities and plan/workspace documentation, then distinguish advertised availability from availability in the teacher's account. Use a teacher-reported model-picker label or an already authorised local selector. Looking up a public model does not require inspecting an account. Compare the task requirements (rubric reasoning, long documents, visual slides, language, or accessibility), eligible models and usage limits. Recommend one **specific model and family**, explain why it suits this review, name one alternative where useful, and let the teacher choose. Record the date and sources. Check actual model identity if the host selects “Auto”. A model with a different family offers an additional perspective and can still miss the same error.

For example, for a GPT-authored redesign with a long rubric, Claude Opus 5.5 could be a candidate if current first-party information supports the task and the teacher's existing approved Claude account offers that model. For a Claude-authored redesign, a named GPT model from the institution's allowed picker may be suitable. Refresh the examples before recommending anything. A provider's API catalogue or benchmark establishes neither subscription entitlement nor teaching quality. [Anthropic model information](https://www.anthropic.com/claude/opus) · [OpenAI model and plan guidance](https://help.openai.com/en/articles/20001354-gpt-6-and-other-models-in-chatgpt) · [Gemini Apps limits and access](https://support.google.com/gemini/answer/16275805)

If identity, remaining allowance, plan terms or the permitted receiving environment cannot be established, say exactly what is unknown. Offer a copyable local review brief, a human colleague or Skip. Never purchase, top up, create an API key, enable a connection or switch billing to complete this step.

## Choose the app and explain independence

First look for a suitable **unused model family in the same app**, on the teacher's approved account. Offer that route first. If the current app has no suitable unused family, offer to use another named, signed-in app with an unused family through scoped computer use, or prepare a manual handoff. Let the teacher choose the recipient and route. A model option visible in a picker is a candidate; check which model actually runs. The final transfer decision applies even when the receiver is in the same app.

If every eligible family contributed, show what each did on this redesign. Offer the least-involved suitable family for a **limited second look**, preferably a different family from the primary author of the selected output. Explain its contribution and why it can still help. Ask the teacher to choose this limited review or finish. If only the primary author's family is available, distinguish a different model in that family from the exact same model performing a self-check. Describe both as limited checks. Never label a participating family or unknown model as independent. Without reliable contribution evidence, say what's unknown and offer a human/manual review or finish. A choice to receive a limited review still needs the separate approval of the exact packet before any transfer.

## Prepare the smallest packet

Within the existing conversation, draft a neutral review question and a short step-by-step record for **all nine core steps**. Include the decision or evidence available at each step, identifying skipped, inapplicable or unverified steps explicitly. Include only the output versions the teacher selects, naming the exact page, slide, question or task where practical. A process-only review can have zero attachments. Keep all original source materials excluded by default. To add an original, obtain a separate, item-specific selection after checking that the handling policy permits that exact material to reach that particular recipient. Permission to use a file earlier in the course does not cover a new reviewer.

Show the exact outgoing text and file list before transfer. Minimise and inspect the selected copies, including comments, notes, hidden slides/sheets, tracked changes, metadata and linked content. Remove student identifiers, grades, credentials, answer keys and private assessment data. Substitute a synthetic excerpt or omit the item when an adequate review cannot respect its access boundary. Keep raw chat history, browser links with tokens, approval receipts and control records local. No folder, account or LMS access is delegated to the reviewer.

## Make the last decision immediately before sending

Offer the manual route first if the receiving app cannot be controlled. The teacher can copy the reviewed prompt and attach the selected files themselves. Preparing text or selecting a subscription authorises no external action. For an assisted transfer, identify the single receiving app and exact workspace/account, audience, model and family, named attachments with revisions, exact prompt/step summaries, purpose, expected plan usage/cost and relevant limits. A new private chat can still send a draft or begin processing when files are attached. Do not paste, attach, upload, type course content into a remote composer, or send anything before a fresh final reply accepting that exact transfer. Never infer permission from interest in a second opinion or a previous tool grant.

Use the existing state validator's optional local record check described below when working from a course project. Immediately before the first remote action match the selected account, model, recipient, packet bytes and access scope with the approved preview. If these change, or the app silently routes to an unknown model, stop and present the corrected preview. Use only the designated receiver via the available browser/computer-use tool. The teacher signs in. Keep every unrelated tab and workspace outside scope. On interruption, first check whether the request reached the intended chat before any retry. If receipt cannot be established, ask the teacher or continue manually.

## Request findings the teacher can check

Ask the reviewer to evaluate what each documented step achieved, whether the selected outcomes, activities and assessment align, and where actual learner/accessible views were checked. For each finding request the exact item and revision, page/slide/question or step, observed evidence, why it matters, a proposed correction and a limitation. Require explicit “unverified” labels where the evidence or original is missing. Ask the reviewer to flag genuine disagreement or uncertainty and avoid inferring steps from a polished file. The prompt, priority order and any findings are advice for the teacher.

Bring back the actual findings or let the teacher paste their manual result. Cross-check each citation against the selected version when authorised. Show the strongest actionable observations with their references and any conflicting or unsupported claims. Ask the teacher which suggestions to accept, amend, defer or reject. A second opinion grants no write, publication or system authority. For selected changes use a fresh authorised revision run with exact targets, preserve originals, show the revised copy, rerun the affected learner checks and obtain the teacher's decision. If nothing changes, finish.

## Optional local transfer record

A teacher-led review can stay in chat. For an assisted transfer in a configured course project, prepare a separate local JSON record in the agreed restricted QA location. Keep the original run terminal. Validate it with `python scripts/validate_state.py STATE --second-opinion RECORD`. This reads two local records and prints the digest of the bound packet. Show the actual packet in human language. After the teacher explicitly approves it, set `approval` to the resulting `packet_sha256` and the actual `reply_reference` as a two-field object. Run the same command with `--require-transfer-approval` before sending. A clean result checks record consistency only. Verify the live teacher reply, destination, content and file hashes separately. The validator never opens attachments or contacts a reviewer.

The record has `run_id`, `packet` and optional `approval`. The packet has `author_families` (a list), `destination` (app, account, audience, exact model, family, cost and access evidence using fields `app`, `account`, `audience`, `model`, `family`, `cost`, `access_evidence` and `billing_basis`, which is either `existing_subscription` or `free`), `prompt` (the exact review question), `steps` and `items`. Each step has its numeric `step` from 1 through 9, `status` (completed, skipped, unverified or inapplicable) and exact outgoing `summary`. Each item has `name`, `revision`, `sha256`, `kind` (output or original) and its local `disclosure_reference`. Each original additionally has a separate `original_selection_reference`. Local references and hashes bind the evidence and stay out of the reviewer's prompt.

For a teacher-selected review by a contributing family, add a local `limited_review` object inside the packet. Record the `kind` (limited_second_look, same_family or same_model), `primary_family`, `primary_model`, currently eligible `eligible_families`, each contributor family’s role in `contributions`, the selection `reason` and the teacher’s separate `reply_reference`. This disclosure is shown locally before the final send decision. Omit the object for an independent review.
